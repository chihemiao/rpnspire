# 3.0 调试与测试设计

> 状态：设计稿，未开始实现。架构见 [架构设计](02-architecture.md)。

## 1. 要解决的问题

| 现在 | 后果 |
|---|---|
| 桌面测试用的是数值 mock（`testcas.lua`），不是 TI 的 CAS | 精确结果的写法、CAS 读不懂的输入、TI 特有的返回格式，只有在真机上才暴露 |
| 真机上出错只有一条提示（“Error: …”），没有上下文 | 无法知道是哪个 CAS 调用、什么输入、多慢 |
| 卡顿只能靠用户描述（“有时候很卡”） | 不知道是 CAS、采样、布局还是重画 |
| 网站模拟器靠手写的 `recorded.lua` 提供精确答案 | 每改一次解题器发给 CAS 的字符串，就要手动更新 |
| 用户报告问题时说不清输入 | 复现要猜 |
| 测试文件 2256 行，界面测试依赖行的顺序（`{down*9}`） | 改布局就要改一堆测试和教程 |

目标：**真机上的每个问题都能被看到、被记录、被带回桌面复现，并变成一个回归测试。**

## 2. 运行时可观测性

### 2.1 日志（`base/log.lua`）

```lua
log.debug('cas', 'solve', { expr = e, ms = 12 })
log.warn('num', 'fallback to CAS per point', { fn = 'f11(x)' })
log.error('topic.graph', 'analysis failed', { phase = 'asymptotes', err = msg })
```

- 环形缓冲区，默认保留最近 300 条（数量可配，体积可控）。
- 级别：debug / info / warn / error。release 构建默认只记 warn 以上；dev 构建记全部。
- 每条带：时间（`timer.getMilliSecCounter`）、模块标签、当前题目 id 和主题 id（由控制器设置的“上下文”）。
- 输出端可插拔：真机写缓冲区；网站模拟器同时写浏览器 console；桌面测试写到 stderr（`VERBOSE=1`）。

### 2.2 CAS 调用记录（`cas/engine.lua` 内置）

每次调用都记录：`{ expr, result, err, ms, memo = hit|miss, job = 'graph#3', phase = 'asymptotes' }`。

- 调试面板显示：本次求解的调用次数、总耗时、最慢的 10 次、记忆化命中率。
- 同一表达式在一次求解里被调用两次以上时记一条 warn（说明缺缓存）。
- 这份记录同时是 **录制** 的数据源（§4）。

### 2.3 计时和内存（`base/prof.lua`）

```lua
local sp = prof.span('graph.asymptotes')  ...  sp:stop()
```

- 每个阶段（解析、求解的各个阶段、vm 重建、布局、绘制、图像采样）都有一个 span。
- 每次重画记录：画了多少行、多少次 gc 调用（录制的 gc 包装可以计数）、耗时。
- 内存：在求解前后、打开全屏图前后记录 `collectgarbage('count')`；调试面板显示峰值。真机上的堆上限没有公开数字，3.0 要用这个实测出来，再定体积和缓存的预算。

### 2.4 调试面板（`debug/panel.lua`，只在 dev 构建或在设置里打开）

menu › Debug 打开，分页：

1. **Summary**：版本、构建类型、apiLevel、内存（当前/峰值）、上次求解耗时、CAS 次数。
2. **CAS**：最近一次求解的调用列表（可以滚动，选中一条看完整表达式和结果）。
3. **Log**：日志缓冲区，按级别过滤。
4. **Facts**：当前题目的 FactGraph（每个结论的 id、依赖、步骤数），用来检查“答案的步骤为什么是空的”。
5. **Rows**：当前行列表（key、kind、高度），用来查布局问题。
6. **Export**：见 §3。

还有一个“跟踪模式”开关：打开后，每个答案的步骤末尾附上它用到的 CAS 调用（只给开发者看）。

### 2.5 断言（`debug/asserts.lua`）

dev 构建里自动检查不变量，失败时记 error 并在页面顶部显示红条（release 构建里这些检查不存在）：

- FactGraph：依赖都存在、无环、每个主答案有步骤（或声明了不需要）。
- 行：key 唯一；选中的行存在；展开状态指向存在的结论。
- i18n：用到的消息 id 存在、参数齐全。
- 缓存：缓存的 FactGraph 在 present 之后没有被修改（dev 构建里给缓存对象加只读元表）。

## 3. 把问题带出计算器

### 3.1 错误边界

每个意图、每个任务都在 `xpcall` 里执行（有 `debug.traceback` 就用它，没有就只记错误消息，因为 TI 上 `debug` 库不一定完整）。出错时：

1. 用户看到一句友好的提示（“这一步没算出来，已记录。menu › Debug › Export 可以导出”）。
2. 日志记一条 error，带上：主题、输入、当前阶段、最近 20 次 CAS 调用、traceback。
3. 不会把半成品结果放进缓存（2.4 修过的“视图出错污染缓存”这一类问题在框架层面杜绝）。

### 3.2 导出（Export）

| 内容 | 格式 | 用途 |
|---|---|---|
| 题目快照 | 一行文本：`vce3:graph:f=(x^2-3)/(x-2);xwin=-6,8` | 发给别人、贴到网站反馈表、在桌面复现 |
| 问题报告 | 多行文本：版本、构建、快照、最近日志、最近 CAS 调用 | 贴到网站反馈表 |
| CAS 录制 | Lua 表的文本：`{ ["expr"] = "result", … }` | 变成测试夹具（§4） |

导出方式（真机没有文件系统）：

- **复制到剪贴板**：在 TI-Nspire 电脑版软件（学生版/教师版，带真实 CAS）里运行时，剪贴板就是电脑的剪贴板，可以直接粘贴到文件里。这是收集“真 CAS 结果”的主要途径。
- **存到文档变量**：`var.store('vce_dbg', text)`，随 `.tns` 一起保存。以后可以用网站的 USB 功能把文档读回来（需要实现“从计算器读取文件”，P3）。
- **显示成可选中的文本页**：最后的办法，用户拍照。

## 4. 录制与回放：用真机 CAS 的结果做测试

这是 3.0 测试设计里最重要的一项，用来解决“mock 不是 TI CAS”。

```
在 TI 电脑版软件（或真机）里打开 dev 构建
  → Debug › Record：开始录制
  → 运行一组题目（自检用例会自动全部跑一遍）
  → Debug › Export CAS recording：复制
  → 粘贴到 tests/fixtures/cas/<主题>.lua
桌面测试：CAS 后端 = replay(fixture) → 未录制的表达式回退到 mock，并记一条 “未录制” 警告
```

- **replay 后端**：命中录制就返回真 CAS 的结果；没命中时，在“严格模式”下直接失败（CI 用于核心用例），在“宽松模式”下回退到 mock。
- **漂移检测**：当解题器改了发给 CAS 的字符串，旧录制会对不上，测试报出“这些表达式没有录制”，提醒去真机上重新录。
- **网站模拟器**：同一套录制文件代替手写的 `recorded.lua`，构建网站时打包进去。
- 录制文件按主题分开，有版本号（TI OS 版本、工具箱版本），方便以后对比不同 OS 的差异。

## 5. 测试分层

| 层 | 测什么 | CAS 后端 | 速度 | 位置 |
|---|---|---|---|---|
| 单元 | `base`、`cas/expr`（解析/打印往返）、`cas/input`、`cas/num`、`mathx/*` 的纯函数、`geom3` 的解析和格式化 | mock 或不需要 | 很快 | `tests/unit/` |
| CAS 契约 | `cas/ops` 对真 CAS 返回值的解析（`solve` 的各种返回格式、`or`、`@n1`、无解、全体实数） | replay（严格） | 快 | `tests/contract/` |
| 主题金样 | 每个主题的每个用例：输入 → FactGraph 的快照（id、值、近似值、依赖、步骤文本）；和保存的“金样文件”比较，差异要人工确认后更新 | replay + mock | 中 | `tests/topics/` |
| 对照（迁移期） | 同一输入，2.x 解题器的数值答案和 3.0 主题的数值答案一致 | mock | 中 | `tests/parity/` |
| 界面 | 用意图和按键驱动应用：选中、展开、离开输入框、任务取消、esc 行为；**按行 key 定位，不按行数** | mock | 中 | `tests/ui/` |
| 性能预算 | 每个示例题的 CAS 调用次数、采样次数、vm 重建次数不超过预算 | mock（计数） | 快 | `tests/budget/` |
| 构建 | 体积预算、Lua 5.1 沙盒冒烟、英文产物无中文、层次依赖检查、luacheck | — | 快 | `tools/` |
| 网站 | 教程（语义按键脚本）在模拟器里能跑通并得到预期答案；USB 发送协议 | replay | 中 | `site/test/` |
| 视觉（P2） | Playwright 在网站模拟器里截关键屏幕，和基准图比较 | replay | 慢 | `site/test/visual/` |
| 真机（手动） | 每次发布前在 CX II 上跑 Help › Self-test，并导出结果 | 真 CAS | 慢 | 发布清单 |

规则：

- 每修一个 bug，先写一个能复现它的测试（金样、界面或契约其中一层）。
- 测试按文件拆分，一个主题一个文件，可以单独运行（`lua tests/run.lua topics/graph`）。现在只能整套跑或者靠临时脚本过滤。
- 自检用例（`cases`）和桌面测试共用一份数据：每个主题的 `cases.lua` 同时用于真机自检和桌面金样。

## 6. 自检 2.0（真机上）

- 按主题分组运行，可以只跑一个主题。
- 跑在任务里（分段执行，不冻结界面），显示进度，可以取消。
- 每个用例记录：通过/失败、耗时、CAS 次数。
- 结果可以导出（§3.2），和桌面的预期值比较。
- 失败的用例可以直接“打开为题目”，看到完整的答案和步骤。

## 7. 开发工具

| 工具 | 作用 |
|---|---|
| `tools/run.lua <快照>` | 在桌面用 replay 后端运行一个题目快照，打印 FactGraph 和步骤（复现用户报告） |
| `tools/screens.lua` | 在桌面渲染指定屏幕的行列表（文字版），用于快速看布局 |
| `tools/arch_check.lua` | 检查层次依赖（见架构设计 §4） |
| `tools/size_report.lua` | 每个模块在 bundle 里占多少字节，超预算时指出最大的模块 |
| `tools/i18n_check.lua` | 消息 id 和参数在 en/zh 两边一致 |
| `tools/fixture_diff.lua` | 比较两份 CAS 录制（不同 OS 版本、不同时间） |
| 网站模拟器 dev 模式 | 加载 dev 构建，Debug 面板可用，console 同步输出日志 |

## 8. 发布前检查清单

1. 全部自动测试通过（Lua 5.4 和 5.1）。
2. 体积在预算内；英文产物无中文。
3. 在 TI 电脑版软件里打开 dev 构建，跑自检，导出 CAS 录制，和仓库里的录制比较；有差异就更新夹具并检查金样。
4. 在 CX II 真机上打开 release 构建，跑自检，记录结果和耗时。
5. 打开一份 2.x 保存的文档，确认历史题目都升级过来了。
6. 记录这次验证的结果（按 AGENTS.md：Lua 测试或 Luna 转换成功不等于在 CX II 上能正常打开和运行，真机验证要单独记录）。
